# Архитектурные решения

## PostgreSQL, а не файлы в контейнере
Выбирал между встроенным хранилищем и отдельной СУБД. PostgreSQL добавляет отдельный компонент, зато даёт транзакционную запись и понятный persistent volume. Для production базу вынес бы в управляемый сервис.

## StatefulSet с PVC для базы
Для базы выбраны StatefulSet и отдельный PVC, потому что идентичность pod и жизненный цикл данных важнее горизонтального масштабирования. Один экземпляр — учебное упрощение; реальную отказоустойчивость здесь не строим.

## Манифесты Kubernetes вместо Helm
Манифесты оставляют ресурсы видимыми и уменьшают число понятий для защиты. Цена выбора — повторение окружений; при нескольких средах перешёл бы на Kustomize или Helm values.

## Ingress и Traefik в k3d
Ingress даёт единый HTTP вход и соответствует учебному кластеру k3d с Traefik. Для внешнего production трафика добавил бы TLS, DNS и контроллер с явно управляемой конфигурацией.

## Compose для локального стека
Compose поднимает приложение, базу и реестр одной командой. Именованный том отделяет данные от жизненного цикла контейнера; `down -v` оставлен явным удалением данных.

## Счётчики приложения в памяти
Минимальные метрики сделаны без дополнительной зависимости и подходят для демонстрации формата Prometheus. При нескольких pod значения разделены и теряются при перезапуске; в production использовал бы клиентскую библиотеку.

## CI deploy вручную по main или Git-тегу
Публикация и ручной deploy происходят только из main или тега. Это ограничивает неожиданные изменения в кластере и сохраняет тег образа как версию для отката; production потребовал бы approval и неизменяемого registry.
