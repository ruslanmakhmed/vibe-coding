# Эскиз AWS-варианта

Для учебной демонстрации кластер k3d, PostgreSQL и мониторинг остаются локальными. При переносе в AWS я бы использовал EKS для Kubernetes, ECR для образов и Application Load Balancer Controller для входящего HTTP(S) трафика. DNS в Route 53 направлял бы на балансировщик, TLS завершался бы сертификатом ACM.

Базу можно оставить StatefulSet на EBS CSI volume либо вынести в Amazon RDS for PostgreSQL. StatefulSet сохраняет схожесть с учебной архитектурой и контроль над параметрами, но команда сама отвечает за обновления, резервные копии и восстановление. RDS даёт управляемые резервные копии и патчи, уменьшает операционную нагрузку и упрощает рост; за это платим сервисом и зависим от сетевой границы. Для прикладного сервиса выбрал бы RDS Multi-AZ после определения требуемого RPO/RTO.

Приложению не нужны долговременные AWS ключи. Для EKS применил бы IAM Roles for Service Accounts (IRSA) или EKS Pod Identity с минимальной IAM ролью; для доступа к секретам использовал бы Secrets Manager CSI driver либо External Secrets с ролью pod. CI runner получал бы краткоживущие credentials через OIDC federation, а не ключ в переменной или файле репозитория.

Снаружи открыты только HTTPS на ALB. Узлы и база находятся в private subnets; PostgreSQL принимает соединения только от security group приложения. Доступ к Kubernetes API ограничен сетевым allowlist или private endpoint. Логи и метрики отправлялись бы в CloudWatch/Prometheus, административный доступ — через SSM Session Manager.

Порядок затрат при небольшом стенде обычно таков: постоянно работающие EKS control plane и worker nodes, затем RDS, затем NAT gateways и балансировщик; ECR, DNS, логи и хранилище добавляют меньшие, но зависящие от трафика расходы. Перед выбором размеров нужна оценка региона, часов работы, хранения, резервных копий и исходящего трафика. Здесь намеренно нет точных цен: учебное задание не требует аккаунта или платных ресурсов.
